# 05 — 画像認識アーキテクチャ決定文書

**結論（先に3行）**

1. **いま作るべきはモデルではなく、データ構造。** オンデバイス識別は後からいつでも足せるが、観察レコードの形は後から変えられない。**観察に `gbifKey` と原画像を残す**ことだけ今決めれば、将来のオンデバイス化・図鑑増補・モデル学習の全部が後付けできる。
2. **無料枠の天井は約100人/日。** ただし**東アジア4,937種の完全な図鑑（GBIF ID・日本語名つき）を無料で丸ごと取得でき**、オフラインで持てることが分かった。「識別はAPI、図鑑はローカル」に分けるだけで、API依存は識別1回/観察まで削れる。
3. **プライバシー懸念は想定より小さい。** Pl@ntNet は利用規約で「**送信された写真はデータベースに保存しない。識別処理中に揮発メモリに置くだけ**」と明言している。散歩写真を外部に送る設計の主要なリスクが1つ消えた。

**状態**: 完了　**作成**: 2026-09-08　**前提の変更**: 最終的に**モバイルアプリ**にする（ユーザー指示）

---

## 0. この文書が答える問い

> 「このAPIを使ってもいいけど、ユーザーが増えて無料枠に収まらなくなったらどうする。本質的にこのアプリの画像認識に必要な要素は何か」

に答えるための文書です。[01](01-identification-providers.md)〜[04](04-bench-real-conditions.md) の実測を前提にしています。

## 1. 前提が変わった：モバイルアプリ化

「最終的にモバイルアプリにしたい」という決定は、画像認識の選択肢を大きく変えます。

| | Web（現状） | モバイルアプリ |
|---|---|---|
| オンデバイス推論 | TensorFlow.js。**訪問のたびにモデルをDL**、WebGL/WASMで遅い | **Core ML / TFLite がネイティブで動く**。モデルはアプリに同梱、DLは1回 |
| カメラ | ファイル選択中心 | 連写・EXIF・位置情報が自然に取れる |
| オフライン | 難しい | **当たり前にできる** |
| 図鑑データの同梱 | 毎回DL | **アプリに同梱して常時オフライン** |

→ **モバイル前提なら、オンデバイス識別は「あり得る選択肢」から「本命候補」に格上げされます。** Web のままなら現実的でなかった。

## 2. コスト構造の実数

### Pl@ntNet の料金（[01](01-identification-providers.md) 参照、2026-09-08時点）

| プラン | 価格 | 枠 |
|---|---|---|
| Free | €0 | **500 identifications/日**。商用可。「Pl@ntNet の認識APIに基づく」旨の表示が求められる |
| Pro | €1,000/年〜 | 年間量に応じ €0.005 / €0.004 / €0.003 / €0.002 per identification |
| 共通制限 | | **同時20リクエスト**まで。Pro には 1M/日 の安全枠 |

### 何人まで持つか

散歩1回あたりの撮影を **3〜10枚**（＝識別3〜10回）と仮定：

| | 無料枠 500/日 | Pro €1,000/年 |
|---|---|---|
| 1人5識別/日 | **100人/日** | 約1,600人/日 |
| 1人10識別/日 | 50人/日 | 約820人/日 |

- **身内や個人の趣味なら無料で足りる**
- **どこかで紹介されて1日200人来たら、その日で枠が尽きる**
- €1,000/年 ≒ 約16万円/年。個人開発では重い
- 従量換算では **1人1日あたり約4円**

**論点はここです。** 「収まらなくなったら課金する」は選択肢の1つですが、**そもそも識別を叩く回数を構造的に減らせるなら、そちらが先**です。

## 3. 見落としていた前提：写真の行き先（安心材料）

Pl@ntNet 利用規約より：

> 「送信された写真はデータベースに保存されない。識別処理の間、サーバの揮発メモリに保持されるだけである」
> 「保存するのはクエリ履歴（日時と送信画像のURL）であって、画像そのものではない」

→ **散歩写真がPl@ntNet側に蓄積されることはない。** 個人の日記に近いアプリとして、これは重要な安心材料です。「写真を外部に送りたくないからオンデバイス」という動機は、少なくとも Pl@ntNet に関しては弱まります。

（※ GDPR 対応の記載あり。日本のユーザー向けサービスとして別途プライバシーポリシーは必要ですが、それは実装フェーズの話。）

## 4. 新発見：図鑑はオフラインで丸ごと持てる

**これが今回いちばん実務的に効く発見です。**

`GET /v2/projects/k-eastern-asia/species`（**無料枠で利用可、ページング可**）で、東アジアの植物リストを全件取得できました。

| 項目 | 実測値 |
|---|---|
| 収録種数 | **4,937種** |
| `gbifId` を持つ | 4,926種（**99.8%**） |
| **日本語の常用名を持つ** | 4,039種（**81.8%**） |
| 上位科 | イネ科389 / キク科371 / マメ科283 / カヤツリグサ科210 / バラ科209 |
| ファイルサイズ | **640KB**（CSV） |

取得済み: [`data/plantnet-k-eastern-asia-species.csv`](data/plantnet-k-eastern-asia-species.csv)

そして **識別レスポンスの `gbif.id` / 種リストの `gbifId` / GBIF本体の `usageKey` が3者完全一致**することを実測で確認しました（*Lycoris radiata* = 7920353、*Houttuynia cordata* = 5384931、*Osmanthus fragrans* = 3172278）。

→ **[02](02-taxonomy-backbone.md) の整数照合設計は、実データで完全に裏付けられました。**

### 意味すること

**「識別」と「図鑑」は分離できます。**

```
識別（オンライン・有限リソース）  写真 → gbifId          ← ここだけAPI
図鑑（オフライン・無限）          gbifId → 和名・科・特徴  ← 640KBのローカルCSV
```

図鑑参照は一切APIを使いません。**API呼び出しは「1観察につき1回」まで削れます。** 再表示・一覧・検索・詳細画面は全部オフライン。

> ⚠️ **要確認**: このリストをアプリに同梱して配布することが Pl@ntNet の利用規約上許されるか、明示されていません。学名・GBIF ID は事実データで、元をたどれば POWO/Kew の公開チェックリストですが、**公開前に確認が必要**です。代替として GBIF から直接構築する経路もあります（無認証・CC0）。

## 5. アーキテクチャ4案

| | A: 現状延長 | **B: ハイブリッド** | C: 完全オンデバイス | D: BYOK |
|---|---|---|---|---|
| 識別 | 毎回API | **端末で30〜50種判定 → 外れたらAPI** | 端末のみ | 毎回API（ユーザーの鍵） |
| 図鑑 | ローカル | ローカル | ローカル | ローカル |
| 無料枠での上限 | 100人/日 | **約300人/日**（端末ヒット率70%想定） | **無制限** | 無制限 |
| オフライン | ✗ | **△（収録種のみ可）** | **○** | ✗ |
| 未収録種 | ○ 対応可 | ○ 対応可 | **✗ 不可** | ○ |
| 実装コスト | 低 | **高**（学習パイプラインが要る） | 高 | 中（UXが重い） |
| いま作れるか | ○ | **△ 段階的に** | △ | ○ |

### C（完全オンデバイス）を推さない理由

散歩の楽しさは「**知らない植物に出会うこと**」です。30〜50種しか判定できない端末モデルだけにすると、**図鑑にない植物に出会ったときに何も言えなくなる**。「バラ科の何からしい」すら返せません。これは体験の中核を削ります。

### D（BYOK）を推さない理由

ユーザーに「my.plantnet.org でアカウントを作ってAPIキーを取ってアプリに貼ってください」と要求することになります。散歩アプリの体験として重すぎます。**ただし「上級者向けの逃げ道」としては優秀**で、無料枠が尽きたときの緊急弁になります。

### B（ハイブリッド）が本命

- よく見る30〜50種は端末で即答（無料・オフライン・高速）
- 珍しいもの・未収録のものだけAPIへ
- **API呼び出しが構造的に減る**ので、無料枠のまま人数が伸ばせる

## 6. オンデバイス識別の実現可能性

Bを取るなら、ここが成立するかが全てです。調べた結果：

### 6-1. モデルサイズは問題にならない

| モデル | サイズ |
|---|---|
| MobileNetV3-Small | **1.99 MB** |
| MobileNetV3-Large | **4.88 MB** |
| （比較）AlexNet | 227.5 MB |

アプリへの同梱で全く問題ない大きさです。

### 6-2. 先行事例がある

「**Leafy AI**」という研究事例が、**112種の観賞植物を67,200枚で学習**し、MobileNetV2 + TensorFlow Lite で Flutter アプリに載せて端末内完結で動かしています。

→ **1種あたり約600枚**が実績値。30〜50種なら **18,000〜30,000枚**が目安。

### 6-3. 学習データは調達できる

| 出所 | 内容 | ライセンス |
|---|---|---|
| **Pl@ntNet-300K** | **306,146枚 / 1,081種**、31.7GB | **CC BY 4.0**（引用必須）。学習済み ResNet18/50 も公開 |
| GBIF occurrence media | 標本・観察写真 | 多くが CC。要フィルタ |
| Wikimedia Commons | 今回のベンチで実証済み | CC各種 |
| **ユーザーの訂正データ** | アプリが貯める | **自前。最も価値が高い** |

**Pl@ntNet-300K が CC BY 4.0 で公開されている**のは大きい。1,081種に対象種が含まれていれば、そのまま fine-tuning の土台にできます（含有確認は未実施）。

### 6-4. 最大の難所：「うちの図鑑にない」をどう判定するか

閉集合の分類器は、**学習していないものを必ずどれかに分類してしまいます。** 猫を見せれば「タンポポ 0.9」と答える。これが **open-set recognition / OOD検出** の問題です。

調べた範囲での実用的手法：

| 手法 | 内容 |
|---|---|
| MSP（最大softmax確率） | 最も単純なベースライン。**過信しやすい** |
| **Energy score** | ロジットから計算。**MSPより明確に優れる**と複数論文が報告。実装が単純でモデル改変不要 |
| OpenMax | 極値理論で活性ベクトルの分布をモデル化 |
| プロトタイプ距離（ARPL等） | 学習した各クラス代表点からの距離で判定 |

→ **Energy score が費用対効果で最良**。既存の分類器にそのまま足せます。

ただし [04](04-bench-real-conditions.md) の実測が示すとおり、**Pl@ntNet ですら「舗装＋苔」を *Sporobolus fertilis* score 0.024 で返しました**。自前モデルで安定した棄却を作るのは相応に難しい、と見るべきです。**ここが B案の最大リスク**です。

### 6-5. モバイル実装の道筋

現状は Vite + React + TypeScript（three.js の3D庭あり）。

| 道 | 既存コードの活用 | オンデバイス推論 |
|---|---|---|
| **Capacitor** | **ほぼ全部そのまま動く**（WebView） | Capawesome の ML Kit プラグイン経由。**ML Kit の Image Labeling はカスタムTFLiteモデルに対応** |
| React Native | **UIは全面書き直し**（three.js の庭も） | `react-native-fast-tflite`（iOSではCore ML/Metalデリゲート）が成熟 |
| PWA | そのまま | TF.js のみ。遅い・毎回DL |

→ **Capacitor が既存資産の観点で圧倒的に有利。** 3Dの庭を作り直さずに済みます。オンデバイス推論も ML Kit のカスタムモデル経路で到達可能。

## 7. 推奨アーキテクチャ：段階的ハイブリッド

**いま全部作るのは間違いです。** オンデバイス化には数万枚の収集と学習パイプラインが要り、しかも**ユーザーの訂正データが貯まってから作ったほうが良いモデルになります**。

### Phase 1（いま）— API + オフライン図鑑

やること:

| # | 内容 | 根拠 |
|---|---|---|
| 1 | **観察レコードに `gbifKey` を保存する** | ← **最重要。後から変えられない唯一の決定** |
| 2 | **原画像を端末に残す** | 将来の学習データ。捨てたら二度と戻らない |
| 3 | 東アジア種リスト（640KB）を同梱し、図鑑参照をオフライン化 | API呼び出しを1観察1回に |
| 4 | 属を主役にしたUI（「アジサイの仲間です」） | 実測で属88% |
| 5 | HTTP 404 を「植物が見つからなかった」として正常分岐 | [04](04-bench-real-conditions.md) |
| 6 | `commonNames` から日本語を選ぶ | 下記 §9 |
| 7 | ユーザーの訂正を記録する | Phase 2 の学習データになる |

### Phase 2（人が増えたら）— オンデバイス第一段を追加

- 30〜50種の MobileNetV3 分類器（約5MB）を同梱
- Energy score で「図鑑にない」を判定 → API へフォールバック
- Phase 1 で貯めた訂正データを学習に使う

### なぜこの順番か

**オンデバイス化は後からいつでも足せます。** 識別の入口を1箇所にまとめておけば、そこに端末モデルを差し込むだけです。

一方 **`gbifKey` を保存していない観察データは、後から紐づけ直せません。** 和名の文字列だけで保存すると、図鑑を増補しても既存の観察は豊かになりません。**今決めるべきはモデルではなくデータ構造だ**、というのがこの文書の結論です。

## 8. いつ破綻するか（撤退ライン）

| 兆候 | 意味 | 打つ手 |
|---|---|---|
| 1日の識別が400回を超える | 無料枠まであと2割 | Phase 2 を着手／BYOKを逃げ道に |
| 同時20リクエストに当たる | 瞬間的な集中 | キューイング。バッチ識別（＝「持ち帰って調べる」設計なら自然に解決） |
| 未収録種の遭遇率が高い | 30〜50種スコープが体験に合っていない | 種数を増やす。Phase 2 の価値は下がる |
| Pl@ntNet の規約・料金変更 | 単一プロバイダ依存のリスク | `gbifKey` を主キーにしてあれば**プロバイダ差し替えが容易**（[02](02-taxonomy-backbone.md)） |

**最後の行が重要です。** GBIF を主キーにしておくこと自体が、プロバイダ依存に対する保険になっています。

## 9. 未回答の論点：識別はいつ起きるか

「その場で即時」か「持ち帰って家で」かは**まだ決まっていません**。技術ではなく体験設計の判断なので、材料だけ置きます。

| | その場で即時 | 持ち帰って後で |
|---|---|---|
| 体験 | 撮った瞬間に名前が出る爽快感 | 「帰ってから図鑑を引く」時間そのものが体験になる |
| 圏外 | **致命的**（散歩先で電波が悪いと機能しない） | 無関係 |
| 通信量 | 都度アップロード | Wi-Fi でまとめて |
| コスト制御 | 難しい | **バッチ処理でき、1日の上限も設けやすい** |
| 同時20リクエスト制限 | 当たりやすい | **当たらない** |
| オンデバイスの価値 | **非常に高い**（圏外を解決する唯一の手段） | 中（あれば速い程度） |

→ **「持ち帰って後で」を選ぶと、Phase 2（オンデバイス）の緊急度が下がります。** 逆に「その場で即時」を選ぶなら、オンデバイスは体験の必須要件に近づきます。**この1問がロードマップの優先順位を決めます。**

## 10. 過去の調査への訂正

実測により [02](02-taxonomy-backbone.md) の記述に2点の訂正が必要です。

### 訂正1: `species/align` は無料プランで使えない

[02](02-taxonomy-backbone.md) で「Pl@ntNet の `align` でも学名正規化ができる」と書きましたが、実際に叩くと：

```
You have no quota for 'align' requests
```

**Pro 専用**でした。ただし **GBIF の `species/match` は無認証・無料で使える**ので、02の推奨（GBIFを使う）はそのまま有効です。

### 訂正2: `gbif.id` は種より上の階級で欠落する

[02](02-taxonomy-backbone.md) では「124候補すべてで返る（100%）」でしたが、[04](04-bench-real-conditions.md) で2件の欠落を確認：

- `Taraxacum sect. Taraxacum`（節レベル）→ gbif なし / powo あり
- `Hydrangea spp.`（属レベル）→ **gbif も powo もなし**

**属を主役に据えるなら、この経路は例外ではなく主要動線**になります。`species.genus.scientificNameWithoutAuthor` の併用が必須です。

（なお種リスト側では 4,926/4,937 = 99.8% が `gbifId` を持つので、**種レベルなら実質全件**と考えて問題ありません。）

## 11. `commonNames[0]` バグの全数調査

[03](03-plantnet-measurement.md)・[04](04-bench-real-conditions.md) で見つけた問題を、東アジア4,937種の全件で定量化しました。

| | 種数 | 割合 |
|---|---|---|
| 常用名を持つ種 | 4,075 | — |
| **うち `[0]` が日本語**（現行コードが正しく表示） | 2,963 | **72.7%** |
| うち**どれか**が日本語 | 4,039 | 99.1% |
| **→ 日本語名があるのにローマ字を表示してしまう** | **1,076** | **26.4%** |

例（左が現行コードの表示、右が正しい和名）:

| 学名 | `commonNames[0]` | 正しい和名 |
|---|---|---|
| *Abies homolepis* | `Dake momi` | ウラジロモミ |
| *Abies veitchii* | `Shirabe` | シラビソ |
| *Acer buergerianum* | `Tō kaede` | トウカエデ |
| *Abutilon theophrasti* | `Ichibi` | イチビ |

→ **`commonNames` からカナ・漢字を含む要素を選ぶだけで、99.1%の種で正しい和名が出ます。** 1行の修正で26.4%の表示が直る、費用対効果の極めて高い修正です（実装はCursor側の担当）。

## 追記：§6-3 の訂正（2026-09-08、[12](12-training-data-availability.md)）

「Pl@ntNet-300K が fine-tuning の土台になる（含有確認は未実施）」と書きましたが、**確認したところ使えませんでした。**

- 選定50種のうち Pl@ntNet-300K に収録されているのは **8種のみ**、同属の種は **ゼロ**
- 1,081種は **303属に偏ったMLベンチマーク**（Sedum 61種、Acacia 39種…）で、日本の植物はほぼ含まれない

**代替は GBIF です。** 選定50種で世界182万枚・日本5万枚の写真つき記録があり、**商用利用可（CC0 / CC BY 4.0）だけに絞っても 46/50 の種が600枚以上**を確保できます。§7 の Phase 2 構想は、データ源を差し替えるだけで維持できます。
