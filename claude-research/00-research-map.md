# 00 — 写真から植物を当てて、自前データと照合する：問題分解とリサーチ設計

**結論（先に3行）**

1. 「写真→植物がわかる」は **1つの技術ではなく3層**。①写真→学名（識別）②学名→正規化された同定キー（照合）③同定キー→和名・特徴（知識）。混ぜて考えると必ず詰まる。
2. 現行実装は **①だけが繋がっていて、②が無く、③が空**（`server/plantnet.ts` の `trait` は固定文字列）。体験の核は③で、詰まるのは②。
3. 精度の議論は **自前の実写真ベンチ（20〜30枚）** を作るまで始めない。カタログ比較は結論を出さない。

---

## 1. 現状の棚卸し（2026-09-08 時点のコードから）

| 層 | 現状 | ファイル |

| ① 識別 | Pl@ntNet API をサーバ経由で呼ぶ。1枚・`organs=auto`・`project=all`・`lang=ja`。APIキー未所持のため**実測ゼロ** | `server/plantnet.ts` |

## 2. 3層モデル

```
 [散歩で撮った写真]
        |
   ① 識別層        写真 → 学名の候補リスト（+ 確信度）
        |          Pl@ntNet / Plant.id / iNaturalist CV / 汎用VLM / オンデバイス
        v
   "Prunus × yedoensis" みたいな文字列（表記ゆれ・シノニム・属止まりあり）
        |
   ② 照合層        学名文字列 → 自前DBの一意キー
        |          正規化・シノニム解決・階層フォールバック（種→属→科）
        v
   taxon:prunus-yedoensis
        |
   ③ 知識層        キー → 和名・科名・特徴・季節・豆知識
        |          自前キュレーション / Wikipedia JA / Wikidata / YList
        v
 [「ソメイヨシノ（バラ科）。3〜4月、葉より先に花が咲く」]
```

さらに全層にまたがるのが **④ 確信度とUXの層**（何%なら断定するか、外したときどう見せるか）。

## 3. 層ごとの「決定に効く問い」

答えが出ても設計が変わらない問いは載せていない。

### ① 識別層

| ID | 問い | なぜ効くか |
|----|------|-----------|
| Q1-1 | Pl@ntNet の `organs`（flower/leaf/fruit/bark/habit）指定と複数枚送信で、精度はどれだけ上がるか | 上がるなら撮影UIが「花を撮ってください」「葉も撮りますか？」に変わる。UX直結 |
| Q1-2 | 日本の身近な草花（園芸種含む）のカバレッジ。`project` パラメータに日本/アジア向けの選択肢はあるか | 公園の園芸品種が全滅なら、このアプリのコンセプトが成立しない |
| Q1-3 | 返ってくる `score` の実際の分布。何%以上なら自動確定してよいか | 閾値がUXの根幹。**実測必須**（→ 5章） |
| Q1-4 | 無料枠 500/日 の実運用上の意味と、キャッシュで削れる量 | 個人利用なら十分か、課金設計が要るかが決まる |
| Q1-5 | 対抗馬（Plant.id / iNaturalist CV / 汎用VLM / オンデバイス）の利用条件・精度・コスト | 乗り換え判断。ただし Pl@ntNet を実測する前にやっても意味がない |
| Q1-6 | スマホ写真の前処理（長辺リサイズ・EXIF回転・JPEG品質）が精度と転送量に与える影響 | base64 で送っている現状、通信量とレスポンス時間に直結 |

### ② 照合層 ← ユーザーの言う「照合」の本体

プロバイダが返す学名は、そのままでは自前DBのキーと一致しない。実際に起きること：

- 表記ゆれ … `Prunus × yedoensis` / `Prunus x yedoensis` / `Prunus yedoensis`
- 命名者付き … `Tulipa gesneriana L.`
- シノニム（異名）… 旧学名で返る／自前DBが旧学名
- 階級のズレ … `Tulipa` （属止まり）、`Rosa sp.`、亜種・変種・品種名つき
- 園芸品種 … `Tulipa 'Apeldoorn'` のような栽培品種名

| ID | 問い | なぜ効くか |
|----|------|-----------|
| Q2-1 | 正規化の標準的なやり方は何か（GBIF Species Match API、POWO/WCVP、Wikidata などのバックボーン） | ここを自作すると必ず破綻する。既存の権威に乗るべき |
| Q2-2 | 主キーを何にするか（GBIF taxonKey / 学名の正規化slug / 自前ID） | データ構造の根幹。後から変えるのが一番高くつく |
| Q2-3 | 解決をオンライン（毎回API）でやるか、**ビルド時に解決済みテーブルを同梱**するか | 後者ならオフライン・即応・無料。有力だが、未収録種に弱くなる |
| Q2-4 | 種で当たらなかったときのフォールバック設計（属→科→「未収録」） | 「バラ科の何か」まで言えれば体験は成立する。全か無かにしない |
| Q2-5 | 和名の権威データはどれか（YList / BG Plants 和名-学名インデックス等）と、その利用条件 | Pl@ntNet の `commonNames` は日本語が薄い可能性が高く、和名は別途要る |

### ③ 知識層

| ID | 問い | なぜ効くか |
|----|------|-----------|
| Q3-1 | 対象種数のスコープは何種か（10 / 100 / 無制限） | **これが全部を決める**。数十種なら自前キュレーションが最高品質で最速。無制限なら自動生成しかない |
| Q3-2 | 自動取得の候補（Wikipedia日本語版API / Wikidata の構造化項目 / POWO）それぞれのライセンスと出典表示義務 | 既に `docs/asset-credits.md` を持つ文化なので、クレジット設計は相性が良い |
| Q3-3 | LLM生成テキストを使う場合の品質保証（出典必須・人間レビュー・誤りの検出） | 植物の記述を間違えるのは、このアプリでは致命傷 |
| Q3-4 | 「特徴」に何を書くと体験が良いか（識別ポイント / 季節 / 由来・和名の意味） | 図鑑の劣化コピーにしない。散歩体験に効く情報を選ぶ |

### ④ 確信度とUX

| ID | 問い | なぜ効くか |
|----|------|-----------|
| Q4-1 | 3段階設計（自動確定 / 候補提示してユーザーが選ぶ / 識別不能）の閾値 | Q1-3 の実測が入力 |
| Q4-2 | 外したときの見せ方 | 誤同定は必ず起きる。「間違えても楽しい」設計が要る |
| Q4-3 | `identificationSource`（sample / plantnet / manual）の正直な表示の維持 | `AGENTS.md` の既存方針。崩さない |

## 4. 調べる順番と停止条件

```
Step 0  自前ベンチを作る（写真20〜30枚 + 正解ラベル）        ← ここから
Step 1  Q3-1（スコープ何種か）を決める                        ← Astra/ユーザーの決定事項
Step 2  ② 照合層を調べる（Q2-1〜Q2-5）                        ← 一番詰まる所を先に潰す
Step 3  ① 識別層をベンチで実測（Q1-1〜Q1-4, Q1-6）            ← APIキー取得後
Step 4  ③ 知識層の調達方法を決める（Q3-2〜Q3-4）
Step 5  ④ 閾値とUX（Q4-1〜Q4-3）
Step 6  必要なら対抗プロバイダ調査（Q1-5）                     ← 現行が不足だと分かってから
```

**なぜ ② を ① より先に調べるか**：識別プロバイダは差し替え可能だが、照合キーの設計は後から変えるとデータ移行が発生する。壊れると高いものから調べる。

**停止条件**：各問いは「Astra が決定を下せる材料が揃った」時点で止める。網羅は目的ではない。

## 5. 自前ベンチ（これが無いと精度の話は全部空論）

散歩で撮った実写真に正解ラベルを付けた小さな評価セットを作る。20〜30枚で十分に判断できる。

- 置き場: `claude-research/bench/`（→ [README](bench/README.md)）
- 測る指標: top-1 正解率 / top-5 正解率 / **属レベル正解率** / score の分布 / 誤同定の傾向
- 条件を混ぜる: 花のアップ・株全体・葉だけ・逆光・群生・つぼみ・雨天

属レベル正解率を測るのが重要。「種は外したが属は合っている」なら Q2-4 のフォールバックで体験は救える。

## 7. 進捗（2026-09-08 更新）

**決定済み（ユーザー判断）**

- Q3-1 対象種数 = **厳選30〜50種を丁寧に**。未収録は属/科フォールバック + 観察のみ保存

| 問い | 結果 |
|---|---|

| Q1-2 プロジェクト | **`k-eastern-asia`（東アジア, 4,937種）** が存在。ただし10枚では結果を変えず（域外種が候補に無かったため）。`useful`（栽培・園芸 5,549種）も候補 |
| Q1-3 score 分布 | **正解時 min 0.162 / 平均 0.619、不正解時 0.651・0.678。逆転している。単一スコアによる自動確定は不可** |
| Q2 前提確認 | `gbif.id` / `powo.id` が **124/124 候補（100%）** で返る。整数照合の設計が実データで裏付けられた |
| 属/科フォールバック | サンプル10枚で **属 10/10・科 10/10**。種を外しても必ず「〇〇の仲間」まで言える |
| 新規発見 | 現行コードの `commonNames[0]` 採用により、**10件中4件でローマ字・別種名が表示される実バグ** |

これにより Q4-1（閾値設計）は「**単一スコアの閾値では設計できない**」という否定的な答えが先に出た。候補提示 + ユーザー確定を前提に、1位と2位が同属かどうかを使う案が次の検証対象。

## 8. 前提の変更とアーキテクチャ決定（2026-09-08 深夜）

**ユーザー指示**: 最終的に**モバイルアプリ**にする。→ オンデバイス識別が現実的な選択肢に格上げ。

**新しく答えが出た問い**（→ [05](05-recognition-architecture.md)）

| 問い | 結果 |
|---|---|
| 無料枠の実質的な天井 | **約100人/日**（1人5識別想定）。Pro €1,000/年で約1,600人/日 |
| 写真は外部に蓄積されるか | **されない。** Pl@ntNet は規約で「画像はDBに保存せず揮発メモリのみ」と明記 |
| 図鑑をオフラインで持てるか | **持てる。** 東アジア4,937種（GBIF ID 99.8% / 日本語名 81.8%）が**無料枠で全件取得可、640KB** |
| オンデバイス識別は成立するか | **条件付きで成立見込み。** MobileNetV3 は 2〜5MB、先行事例は112種を67,200枚で学習。学習データは Pl@ntNet-300K（CC BY 4.0, 306,146枚/1,081種）が使える。**最大の難所は「図鑑にない」の判定（open-set）** |
| モバイル移行の道 | **Capacitor**。既存の Vite+React+three.js がほぼそのまま動く。ML Kit のカスタムTFLiteモデル経路でオンデバイス推論も到達可能 |
| 今すぐ決めるべきこと | **モデルではなくデータ構造。** 観察に `gbifKey` と原画像を残せば、オンデバイス化は後から足せる |

**02への訂正**: `species/align` は **Pro専用**（無料枠では使用不可）。`gbif.id` は**属・節レベルの結果で欠落する**。

**未決**: 識別はその場で即時か、持ち帰って後でか（→ [05 §9](05-recognition-architecture.md)）。オンデバイス化の緊急度がこれで決まる。

## 9. VLM対決と project の決着（2026-09-08）

**ユーザーの疑問「Pl@ntNet 使うの微妙では?」への回答**（→ [06](06-vlm-vs-plantnet.md)）

GBIF の日本の観察記録20枚でブラインドテストを実施：

| | 種一致 | 属一致 |
|---|---|---|
| **Pl@ntNet** | **16/20** | **19/20** |
| 汎用VLM | 15/20 | 15/20 |

- **Pl@ntNet の勝ち。微妙ではない。** さらに誤り方の質が違う：Pl@ntNet は同属の近縁種に外れる（属フォールバックで救える）が、**VLM は科ごと飛ぶ**（救えない）
- ただし **VLM の自己申告確信度は正しかった**（high の9件が9/9正解）。Pl@ntNet の `score` にできないことができている → **確信度レイヤーとしてVLMを使う案**が新たな検討対象
- **Q1-2 決着: `project` は絞らない。** `k-eastern-asia` は精度を下げた。原因は在来フローラのため**セイヨウタンポポ・ワルナスビ等の帰化植物が未収録**であること。散歩アプリの被写体は帰化・園芸種が多いので逆効果

**これで Pl@ntNet 続投は実測で裏付けられた。** 残る弱点は精度ではなく確信度であり、それは「属で括って候補を見せる」設計で回避できる。
